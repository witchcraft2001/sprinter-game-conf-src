# Sprinter DX: IOCHRDY → /WAIT, почему ISA-карты читаются как FF

Дата: 2026-10-16. Ветка `iochrdy-research`. Источники: `altera/acex/K50/SP2_ACEX.TDF`,
`DCP.TDF`, нетлист `board/spdx_release_v306_25.05.2025/pcad/sp-dx.net`, лист 8 `sp-dx-sch.pdf`,
Intel ISA Bus Specification 2.01 (табл. 9.0.1), Zilog PS0182 (Z84C15, табл. A, стр. 348–350),
исходники PicoGUS (`board/picogus/sw/isa/isa_io.pio`, `picogus.cpp`).

## 1. Как устроен путь сейчас (подтверждено нетлистом и исходниками)

Цепь `WAIT/`: U3.11 (Z84C1516), U12.18 (ACEX), R37 1 кОм → +5 В, X28.A38 (Z-slot), VD12 анод.
Цепь `IOCHRDY`: X36..X39 A10 (4 слота), R47 4,3 кОм → +5 В, VD12 катод (LL4148).
У DX Mini тот же путь, но через разъём Z-slot на внешний модуль (ext-cpu-isa): VD12 и R47 там.

Строб чтения: `/MREQ↓` → ACEX защёлкивает `CS_ISA` по спаду `/MREQ` → пин `CS_CASH` →
DD7 74HC138 (E2=CS_CASH, E1=RA16, E0=RA17, A2=RA15, A1=WR/, A0=RA14) → DD20 74HC32 (с RD/) →
R194 51 Ом → `IORD1/`. Итого `/IOR` появляется примерно через 40–50 нс после `/MREQ↓`
(ACEX ~10 нс + HC138 ~20 нс + HC32 ~12 нс).

Данные: U5 74HC245, DIR = RD/, OE = ISA_CS (= CS_CASH or RA16). BD0..BD7 подтянуты 4,3 кОм к +5 В,
поэтому «никто не ответил» читается как FF.

ACEX (`SP2_ACEX.TDF`):

```
/WAIT_ALL = (DECODE./WAIT & WAIT_ROM & WAIT_ORIG);
/WAIT     = TRI(/WAIT_ALL, LCELL(!/WAIT_ALL));
```

* Для окна ISA (страница D0..DF в окне 3, C000..FFFF) из трёх источников реально работает только
  `WAIT_ROM`: общий с ROM счётчик `WT_R = 4` → ожидание ~95–120 нс после `CS_ISA` (5 фронтов CLK42),
  плюс ~10 нс на выход. `DECODE./WAIT` для окна ISA = 1 (MEM_RW), `WAIT_ORIG` = 1 в turbo.
* Вход пина `/WAIT` внутри ACEX не читается нигде. ACEX не знает ни о IOCHRDY, ни о том,
  что карта удерживает линию.
* Выход: DATA = `/WAIT_ALL`, OE = `LCELL(!/WAIT_ALL)`. При отпускании (0→1) DATA становится 1
  раньше, чем OE выключится, то есть несколько наносекунд пин активно тянет вверх.
  Судя по закомментированным вариантам в старых исходниках, это осознанный «ускоритель фронта»
  для подтяжки 1 кОм, он помогал не терять такт на обычных обращениях.

Тактирование: CLKZ1 из ACEX напрямую на U3.69 (режим внешнего клока без деления, вывод EV).
Turbo 21 МГц (T = 47,6 нс), без turbo 3,5 МГц (T = 285,7 нс). Z80 опрашивает `/WAIT` по спаду T2
и каждого TW, данные защёлкивает по спаду T3. Z84C1516: TsD(Cf) = 12 нс, TdCf(MREQf) ≤ 40 нс,
VIL ≤ 0,8 В, VIH ≥ 2,2 В. TsWAIT(Cf) в таблице 75 нс (похоже на опечатку, у 10 МГц варианта 20 нс);
дальше берётся 20 нс.

## 2. Расчётная диаграмма чтения ISA (отсчёт от спада T1)

| Событие | Turbo 21 МГц | Без turbo 3,5 МГц |
|---|---|---|
| `/MREQ↓`, `/RD↓` | +20 (≤40) | +20 |
| `/IOR↓` на слоте | ≈ +65 | ≈ +65 |
| ACEX отпускает `/WAIT` (WT_R=4) | ≈ +135…+160 | ≈ +135…+160 (раньше первого опроса) |
| Точки опроса `/WAIT` Z80 | 47,6 / 95,2 / 142,8 / 190,4 … | 285,7 / 571,4 … |
| IOCHRDY должен быть низким на U3.11 | к ≈ +170 → **≈ 105 нс после `/IOR↓`** | к ≈ +266 → **≈ 200 нс после `/IOR↓`** |
| Данные на BD нужны | к ≈ +216 → ≈ 150 нс после `/IOR↓` | к ≈ +550 → ≈ 485 нс после `/IOR↓` |
| Ширина `/IOR` без ожидания карты | ≈ 220 нс | ≈ 555 нс |

Требования Intel ISA 2.01, табл. 9.0.1 (сторона карты): 20b IOCHRDY↓ не позже 356 нс после
8-битной команды; 8d ширина 8-битной команды ≥ 519 нс; 10d доступ к данным ≤ 467 нс от команды;
22 команда держится ≥ 125 нс после IOCHRDY↑; 25 данные могут появиться до 63 нс после IOCHRDY↑;
7b адрес стабилен ≥ 91 нс до команды.

Выводы из таблицы:

* В turbo цикл в 2,5 раза короче минимального по спецификации и перестаёт слушать IOCHRDY
  через ~105 нс после `/IOR`, хотя карта имеет право опустить его через 356 нс.
  Любая карта, которая не успевает за ~150 нс выдать данные и не успевает за ~100 нс опустить
  IOCHRDY, читается как FF. Запись при этом обычно проходит (данные защёлкиваются по фронту).
* Без turbo «нормальный» 8-битный цикл почти укладывается в спецификацию (555 нс против 519,
  485 нс против 467), поэтому большинство 5-вольтовых карт работает. Но окно для IOCHRDY всё
  равно ~200 нс вместо 356, и это гонка для медленных карт.
* Установка адреса до команды в turbo ≈ 50–60 нс против 91 нс по спецификации. Это патчем не
  исправляется (определяется таймингом Z80), на практике почти все карты декодируют быстрее.

## 3. Что делает PicoGUS (по исходникам прошивки)

PIO-программа `ior` (`isa_io.pio`): по спаду IOR читает адрес, кладёт в FIFO и **ждёт решения
ядра** (`out X,32`) с IOCHRDY ещё не опущенным. Только после `pio_sm_put(IO_WAIT)` из
`handle_ior()` (сравнение адреса с базовыми портами) PIO выполняет `out pins,8 side 0b01`,
то есть опускает IOCHRDY, и держит его до прихода данных, затем выставляет данные и отпускает
IOCHRDY, данные держит до фронта IOR. Ядро на 370 МГц, режим опроса FIFO (USE_IRQ выключен).
Латентность IOR↓ → IOCHRDY↓ получается порядка 100–200 нс, больше, если ядро 1 ещё занято
предыдущей записью (обработчик OPL/GUS).

Следствия для Sprinter:

* turbo: окно ~105 нс, PicoGUS никогда не успевает → FF всегда;
* без turbo: окно ~200 нс против латентности 100–200+ нс → гонка, «иногда работает»;
* записи (`iow`: адрес и данные защёлкиваются PIO через ~10 тактов после IOW↓) проходят даже
  при коротком цикле, поэтому карта инициализируется, а детект AdLib по чтению статуса 388h
  проваливается → «AdLib молчит».

## 4. Дефекты в порядке значимости

1. **Слишком короткое начальное ожидание ISA в ACEX** (главный, объясняет разницу turbo/без turbo
   и разное поведение карт). Лечится прошивкой.
2. **Уровень через диод.** Карта тянет IOCHRDY до ~0,2 В (74LVC2G06 при ~5 мА), на LL4148 при
   4,3 мА (R37) + 1 мА (R47) падает ~0,7–0,75 В → на U3.11 около 0,9–1,0 В при VIL ≤ 0,8 В.
   Реальный порог Z84C15 около 1,2–1,5 В, поэтому «иногда» работает. BAT48 даёт ~0,6 В,
   с R37 = 4,7 кОм ~0,5 В. Только схемотехника.
3. **Активная «1» при отпускании `/WAIT`.** В turbo отпускание приходится на ~135–160 нс, то есть
   на одно из двух положений относительно спада CLKZ1 (≈12 или ≈36 нс до него, в зависимости от
   того, в какой такт CLK42 попал асинхронный спад `/MREQ`). В положении «12 нс» импульс длиной
   5–10 нс попадает в окно setup/hold Z80 (20 нс до спада, 10 нс после) и может быть
   засчитан как «/WAIT = 1», даже если карта держит IOCHRDY. Фаза зависит от задержки выхода
   Z80 (температура, экземпляр), отсюда разное поведение плат. Без turbo импульс далеко от
   точки опроса. Лечится прошивкой.
4. **U5 74HC245 с КМОП-порогами** (VIH ≥ 3,5 В при 5 В) принимает данные PicoGUS через
   SN74CB3T3245 с уровнем ~3,3 В. Это может давать ошибки отдельных битов (1 читается как 0),
   но не FF. Замена на 74HCT245 (VIH 2,0 В) снимает вопрос. Для 5-вольтовых NE2000 неактуально.
5. Без turbo при ALL_MODE2 = 0 и PN2 = 1 к окну C000..FFFF добавляется «спектрумовское»
   ожидание по CT5 (до ~760 нс). Только удлиняет цикл, не ломает.

Отдельно: после того как карта отпустила IOCHRDY, Z80 заканчивает цикл через 1 такт, то есть
удержание команды после READY в turbo ≈ 70–150 нс при минимуме 125 нс по спецификации, а данные,
пришедшие за 63 нс после IOCHRDY↑, успевают с запасом ~10–20 нс. ACEX не может продлить цикл
после READY, потому что не видит IOCHRDY отдельно от собственного `/WAIT`.

## 5. Что сделано прошивкой (изменения в `altera/acex/K30|K50/SP2_ACEX.TDF`)

Параметры в заголовке:

```
ISA_WAIT = 20,      -- /WAIT удерживается (ISA_WAIT+1) тактов CLK42 после CS_ISA (~500 нс)
WAIT_OD  = "ISA"    -- "ISA": 0/Z во время цикла ISA, "ALL": чистый open drain, "OFF": как было
```

Логика:

* Отдельный счётчик `WT_I[4..0]` только для `CS_ISA` (ROM остаётся на `WT_R = 4`).
  `WAIT_ISA` входит в `/WAIT_ALL`. Бит 0 регистра страницы ISA (`ISA_PORT0`, страницы
  D1/D3/D5/D7) включает прежний короткий цикл; существующий софт пишет D4/D6, то есть по
  умолчанию получает длинный цикл. MAME (`sprinter.cpp`, маска `0xF9`) страницы с битом 0 не
  считает ISA, при использовании быстрого режима эмулятор надо будет поправить.
* `/WAIT` в режиме "ISA": `TRI((/WAIT_ALL & CS_ISA), LCELL(!/WAIT_ALL))`. Пока `CS_ISA = 0`,
  DATA = 0, пин бывает только 0 или Z. Вне ISA поведение (ускоритель фронта) не меняется.
  Режим "ALL" (`TRI(GND, !/WAIT_ALL)`) убирает ускоритель совсем и может добавить такт
  ожидания на части обычных обращений; это отдельный эксперимент.

Ожидаемые тайминги с `ISA_WAIT = 20` (отпускание ≈ +540…+560 нс от спада T1):

| | Turbo | Без turbo |
|---|---|---|
| Опрос, который видит отпускание | 571 нс | 571 нс (при разбросе может уйти на 857) |
| Ширина `/IOR` | ≈ 605 нс (≥ 519) | ≈ 840 нс или ≈ 1,13 мкс |
| Окно для IOCHRDY↓ после `/IOR↓` | ≈ 485 нс (≥ 356) | ≈ 485 нс |
| Окно для данных после `/IOR↓` | ≈ 540 нс (≥ 467) | ≈ 770 нс |

`ISA_WAIT = 18` даёт более ровный результат без turbo (всегда 571 нс), но в turbo запас по
данным сжимается до ~15 нс. Цена: одно обращение к ISA в turbo ≈ 620 нс вместо ≈ 240 нс,
копирование пакета NE2000 замедлится примерно в полтора раза; для таких карт можно включать
быстрый режим битом 0 страницы.

Ресурсы: +5 триггеров и ~8 LC, у EP1K30 было 91 %, должно поместиться. Сборка: `make.cmd`
(K30) или `make_k50.bat` (K50) в MAX+PLUS II, как раньше; сборка здесь не проверялась,
синтаксис взят по образцу существующего кода (CASE как у `WT_CT` в DCP.TDF, параметры как
`UPDATE`/`NUM`). Откат: `git checkout altera/acex/K30/SP2_ACEX.TDF altera/acex/K50/SP2_ACEX.TDF`.

Чего прошивкой сделать нельзя:

* убрать падение на VD12 и гарантировать ноль на U3.11;
* продлить цикл после IOCHRDY↑ (параметры 22 и 25 спецификации) и сделать таймаут на зависший
  IOCHRDY (NICREG «висит» именно так): ACEX не видит IOCHRDY, пока сам держит `/WAIT`,
  а читать пин `/WAIT` в отпущенном состоянии бесполезно, Z80 видит ту же линию в тот же момент.
  Для этого нужен вход IOCHRDY в ПЛИС.

## 6. Что только схемотехникой

* Минимум: VD12 → Шоттки (BAT54/BAT48) и R37 → 4,7 кОм (ток через диод ~1 мА, уровень ~0,5 В).
  С убранным ускорителем в режиме "ALL" подъём `/WAIT` на 4,7 кОм станет медленнее
  (τ ≈ 150–250 нс), в режиме "ISA" ускоритель остаётся и это не мешает.
* Лучше: вместо VD12 буфер с открытым стоком 74LVC1G07 (или 74AHCT1G125 с OE на землю)
  на 5 В: вход IOCHRDY, выход на `WAIT/`. Уровень 0,1–0,2 В, никакой зависимости от тока.
* U5 → 74HCT245N (панелька DIP, замена без пайки) для 3,3-вольтовых карт (PicoGUS, PicoMEM).
* Полноценно: IOCHRDY на вход ПЛИС. У ACEX U12 свободных пинов нет (все 208 разведены,
  `/HALT` на 182 не используется, но это цепь HALT/ процессора). У EPM7064 U13 двадцать
  неразведённых пинов (1, 2, 5, 7, 22, 24, 27, 28, 49, 50, 53, 55, 61, 69, 70, 72, 77, 78, 84, 85).
  Два провода (IOCHRDY → вход MAX через 1 кОм, выход MAX с `OPNDRN` → на `WAIT/` вместо VD12)
  и строка в `SP2_MAX_DX.TDF`: `/WAIT_X = OPNDRN(IOCHRDY_S)`. Там же можно сделать удержание
  команды 125 нс после READY и таймаут 15,6 мкс. Это уже отдельная доработка.

## 7. План экспериментов

Без осциллографа (ближайшие дни):

1. Собрать три варианта и прогнать один и тот же набор (PGUSCFG, ADLIBTST, NICREG на UM9003
   и RTL8019) в turbo и без turbo, фиксируя долю FF:
   * A: `ISA_WAIT = 20`, `WAIT_OD = "ISA"` (как в ветке);
   * B: `ISA_WAIT = 20`, `WAIT_OD = "OFF"` (только длинный цикл);
   * C: `ISA_WAIT = 3`, `WAIT_OD = "ISA"` (только убран активный фронт, цикл почти прежний).
   * O: исходный `SP2_ACEX.TDF` (эталон для сравнения на той же плате).
   Сборка всех четырёх: `altera\acex\build_iochrdy.bat [K30|K50] [O A B C]`, результат в
   `altera\acex\iochrdy\out\STREAM_<чип>_<вариант>.BIN`. Параметры подставляет
   `iochrdy\setparam.ps1` (нужен PowerShell), исходники в `K30\`/`K50\` не меняются.
   Если A и B лечат PicoGUS, а C нет, доминирует дефект 1. Если C лечит часть случаев в turbo,
   дефект 3 реален. Остаток нестабильности без turbo при A указывает на уровень (дефект 2).
2. Программная проверка, видит ли Z80 IOCHRDY: замерить время N одинаковых чтений порта
   PicoGUS (1D0h), где карта заведомо держит IOCHRDY, против чтения пустого адреса окна.
   Таймер: CTC Z84C15 или счётчик кадров. Если времена равны, процессор ожидание не видит
   (уровень или полярность диода).
3. Временная перемычка вместо VD12 (на одном экземпляре): убирает падение на диоде и
   объединяет подтяжки. Если без turbo PicoGUS становится стабильным, подтверждается дефект 2.
   Как штатное решение не годится (ACEX будет дёргать IOCHRDY на каждом своём ожидании,
   вырастет ёмкость на `/WAIT`).
4. В зависшем состоянии (NICREG hang) мультиметром: `WAIT/` на U3.11 и IOCHRDY на A10.
   WAIT/ выше 0,8 В при IOCHRDY низком означает дефект 2.
5. U5 → HCT245 перед тестами с PicoGUS, чтобы исключить ошибки битов.

С осциллографом (4 канала): `/IOR` (X36 B14), IOCHRDY (A10), `WAIT/` (U3.11), CLKZ1 (U3.69),
триггер по спаду `/IOR`, одно чтение 1D0h в turbo. Смотреть: задержку IOCHRDY↓ после `/IOR↓`
(ожидается 100–200 нс у PicoGUS), уровень `WAIT/` при IOCHRDY = 0, короткий подъём `WAIT/`
около +135…+160 нс от спада T1 (ускоритель), ширину `/IOR`. Потом то же с новой прошивкой:
`/IOR` должен стать ≥ 520 нс, подъёма быть не должно.
