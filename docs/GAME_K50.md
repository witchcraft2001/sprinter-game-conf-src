# GAME_K50: опытная конфигурация EP1K50QC208-3

Это исходники кандидата для MAX+plus II 10.0, а не подтверждённая прошивка.
Локально проверены спецификационная модель, выражения read pipeline из TDF,
упаковка, код загрузчика TITDREV/BIOS в Z80 и диагностическая DSS-программа. AHDL не компилировался: MAX+plus II/Windows и плата K50 в этой
среде отсутствуют. Fitting, фактическая задержка SRAM/DAC, синхронизация и TITD
остаются обязательными этапами приёмки. Ограниченный интерпретатор исполняет
выражения и CLK42-регистры read pipeline, но не весь AHDL и не netlist.
Результаты кодревью и незавершённые пункты — в [REVIEW_GAME_K50.md](REVIEW_GAME_K50.md).

## Сборка Windows

Нужны MAX+plus II (по умолчанию `C:\MAXPLUS2\MAXPLUS2.EXE`), штатные Windows
`cmd.exe`, Windows Script Host (`cscript.exe`) и `ADODB.Stream`. Python, grep, Unix shell и Quartus для FPGA-сборки не нужны.
Если MAX+plus II установлен иначе, задайте `MAXPLUS2_EXE` полным путём к EXE.

1. Запустите `altera\acex\make_standard_k50.bat`. Сначала проверьте этот SOF на
   плате: стандартный экран, память, клавиатуру, звук и акселератор.
2. Затем запустите `altera\acex\make_game_k50.bat`.
3. Каждый запуск создаёт новый `altera\acex\build\VARIANT-число-число`.
   Совпадение имени каталога считается ошибкой; существующие файлы не используются.
   `make_k50.bat` теперь вызывает чистую **стандартную** сборку.
4. В каталоге сохраняются исходники, `source-files.txt`, `variant.txt`,
   `floorplan-audit.txt`, все диагностические файлы компилятора,
   `compile.log`, `SP2_ACEX.rpt`, `SP2_ACEX.sof`, `SP2_ACEX.ttf`,
   `STREAM50.BIN`, `K50.packed`, `roundtrip.bin` и после успешной проверки `K50.ACX`.
   Ошибка обязательного этапа возвращает ненулевой exit code. Логи не удаляются.
   `acx-sha256.txt` содержит результат дополнительного вызова штатного certutil;
   его отсутствие не заменяет и не отменяет проверки содержимого.

Сборка подставляет только `GAME_K50/VIDEO2.TDF` поверх общих файлов `K50`.
Интерфейс `video2`, экземпляр `video2:SVIDEO`, назначения физических выводов,
логика CPU, акселератора, звука и периферии сохраняются. В staging-копиях всех
ACF выбран `EP1K50QC208-3` для конкретного устройства и timing synthesis.
AUTO_DEVICE-списки не управляют явно выбранным top-level устройством.

Наследованные размещения LC/EAB сохраняются **в обеих сборках** и перечисляются
в `floorplan-audit.txt`. Слепое удаление изменяло бы базовую конфигурацию и
физические задержки LCELL write-тракта. Валидность размещений для K50 и
предупреждения ignored assignments нужно проверить по fitting report. Наличие
аудита не означает успешного размещения. Оригинальные K50 ACF не меняются.

Упаковка использует существующие `transttf.exe` и `Altera0pak.exe`. Проверка:
успех в отчёте, ровно один целевой Device K50, непустые новые SOF/TTF,
строгое соответствие каждого байта TTF/STREAM50, K50 header `FF FF 62 7B 3C 00`,
распаковка штатным packer и независимая проверка zero-run формата. Размер
сжатого ACX должен быть **1…65536 байт**. Превышение запрещает выпуск, без усечения.
В распакованном потоке K50 имеет байт `3C`, K30 — `39`. Сжатый файл начинается
`FF FF 62 7B 3C 00 nn`: `nn` — ненулевой счётчик первого zero-run
(обычно 01; нули после заголовка могут увеличить его). BIOS распознаёт
сжатый K50 по несовпадению с несжатым ROM-заголовком K30 в
`loader/bitstream_header.inc`. В ACX нет EXE-header, длины или 256-байтного
загрузочного префикса: первый байт файла — первый байт zero-packer потока. `package-verification.txt` подтверждает только упаковку.
Не копируйте ACX из каталога предыдущего запуска при ошибке нового.

## Дескриптор и адресное пространство

VRAM — 256 КиБ, 256 строк по 1024 байта, четыре SRAM банка по 64 КиБ.
Логический байт `a` хранится в `VDM[3-(a & 3)][a >> 2]` (видно также из `V_EN3…0`
общего write-тракта). Физические адресные выводы `VAO = VLA[17:2]`.

| Байт | Банк | Семантика game |
|---|---|---|
| MODE0 | VDM3 | биты 1:0 — X[9:8]; бит 2 — загрузить скролл; биты 7:6 — палитра |
| MODE1 | VDM2 | X[7:0], допускается любой адрес, включая невыровненный |
| MODE2 | VDM1 | Y[7:0] |
| MODE3 | VDM0 | младший полубайт — X scroll 0…15; старший — Y scroll 0…15 |

В TITD `src/runtime/entry_runtime.asm` находятся исходные четвёрки
`F4 00 00 00`, `F4 00 00 80`, серия `24 00 00 0F`, затем `E4 00 00 00`.
Они подтверждают отдельный четвёртый байт и загрузку горизонтального/вертикального
смещения, а не часть пиксельных данных. Разложение X/Y проверяется по game renderer
и организации штатного VRAM; точный момент применения в оригинальном FPGA неизвестен.

MODE0[5:3] участвуют в специальных режимах; в обычной game-графике нет
разделения байта на два цвета. Один байт задаёт индекс 0…255. Визуальное
удвоение по горизонтали в MAME не превращает этот формат в 4bpp.

Адрес дескриптора: `(page<<17) | (column<<11) | 0x700 | (row<<2)`.
Здесь `column=sample_x/8`, `row=sample_y/8`, page=`DIR_PORT3`.
Это нечётная строка каждой пары, соответствующая четырёхбайтовым записям TITD
и штатной форме `(DIR_PORT3, CTH, CT5, 11b, CTV[8:3], 00b)` при CT5=1.
Используются все 56 столбцов и 40 строк, включая невидимые.

`sample_x=(physical_x+scroll_x) mod 448`,
`sample_y=(physical_y+scroll_y) mod 320`.
Физические CT/CTH/CTV и COPY_SINC не зависят от scroll. Вертикальный счётчик
по исходной схеме увеличивается в конце CTH=48, а горизонтальный оборачивается
после CTH=55 — модель сохраняет именно эту последовательность.

В этой реализации адрес графики определён так:

```
xbase = ((MODE0 & 3) << 8) | MODE1
ybase = (MODE2 + (sample_y & 7)) & 255
address = (ybase * 1024 + xbase + (sample_x & 7)) & 0x3ffff
```

Сложение X может переноситься в следующую строку, суммарный адрес оборачивается
на границе 256 КиБ. Это явная рабочая семантика для пограничных случаев;
эквивалентность недокументированной оригинальной FPGA не подтверждена.

Скролл — последовательное состояние с нулевым power-up. Управляющий
дескриптор принимается при изменении его адреса (включая номер страницы),
а не при каждом повторном чтении того же адреса. Повторный вход в клетку
считается новым принятием. MODE3 захватывается вместе с остальными байтами;
через один CLK42 его значение загружается в scroll. Текущий пиксель использует
координаты, зафиксированные до этой загрузки; изменение действует со следующего
запроса дескриптора. Запись CPU в MODE3 уже занятой клетки применяется при
следующем входе. Сброса на строке/кадре и MAME `lookback_scroll` нет.
Нулевые power-up G_SCROLL/G_VALID и отсутствие их оптимизации в константы
нужно подтвердить в netlist MAX+plus II для ACEX. Интерпретатор и модель задают
нулевое начальное состояние; это само по себе не проверка аппаратной инициализации.

| MODE0 | Отображение | Scroll | Interrupt request |
|---|---|---|---|
| 24h | байтовая графика, палитра 0 | да | нет |
| E4h, F4h | border, индекс 400h + 9×BRD | да | нет |
| FCh, FEh | blank, индекс 400h | да | нет |
| FDh, FFh | blank, индекс 400h | да | да |

Общий признак border — MODE0[7:5]=111; blank дополнительно требует bits3:2=11
или DIR_PORT4. Interrupt дополнительно требует bit0=1; как в исходнике,
активный низкий INTT регистрируется по фронту **бита CT[5]** при физических
CTV[2:0]=7. Это производный такт внутри клетки, а не фаза CT[2:0]=5.
Обычные палитры выбираются индексом `(MODE0[7:6]<<8)|color`.
Для палитры 3 обычные дескрипторы используют C0h…DFh, не E0h…FFh.

## Фазы чтения

Таблица показывает **значения до фронта CLK42**. После фронта VLA меняется,
а SRAM должна установиться до следующего фронта. Частота 42 МГц даёт 23,81 нс
на полный путь FPGA→SRAM→FPGA, включая setup/hold; 15 нс модели — допущение,
а не измеренная характеристика установленной памяти.

| CT[2:0] | VCM | После фронта VLA | Захват до смены адреса |
|---|---|---|---|
| 0 | 5 | пиксель | — |
| 1 | 1 | тот же пиксель | цвет из выбранного банка, палитра, border/blank/IRQ |
| 2 | 4 | палитра | — |
| 4 | 3 | дескриптор следующего физического пикселя | координаты/адрес запроса |
| 5 | 2 | исходное окно CPU/акселератора | MODE0…3, признак нового control |
| 6 | 0 | палитра | scroll из принятого MODE3; штатное продвижение растра |

WR_MODE по-прежнему опускается при выдаче descriptor slot и поднимается на
следующем фронте, но game-регистры захватываются общим CLK42 с enable VCM=2.
Захват не зависит от задержки производного LWR_MODE. Обе palette-фазы используют
один индекс и согласованные метаданные. SRAM write-тракт оставлен байт-в-байт.
Сдвиг видимого первого пикселя относительно внешнего DAC надо проверить на плате:
новый read pipeline намеренно не копирует старые цепочки derived clock.

## Проверки

Из корня: `python3 -m unittest discover -s tests -v` (Python 3, C-компилятор).
Проверяются полный растр обеих страниц/переход кадра, все 256 сочетаний scroll,
замена/наследование смещений, control справа от экрана, невыровненные адреса,
границы памяти, четыре банка, палитры и специальные дескрипторы, palette latency,
CPU slot и отказ модели при слишком медленной SRAM. Тест также сравнивает
интерфейс, растровые счётчики и write-тракт с исходником K50.
`tools/ahdl_read_sim.py` разбирает непосредственно game TDF и исполняет его
read-выражения, IF/CASE, банк SRAM и CLK42 DFFE с одновременным обновлением.
15 Python-тестов прошли, включая полный растр обеих страниц для TDF и модели;
намеренные повреждения захвата MODE3, банка цвета, фазы scroll и wrap выявляются.
Общие counters/write-тракт проверяются сравнением с K50; электрические задержки,
асинхронные reset и весь derived-clock тракт интерпретатор не исполняет.

`node tests/test_k50_build.js` выполняет **тот же JScript core**, что Windows
cscript: 20 проверок прошли. Проверяются чистый staging, сохранение pins/LC/EAB,
явный K50, отсутствие старых TTF, повреждения, неправильный чип, отсутствие SOF,
предел 65536/65537, TTF и независимая распаковка. WSH COM и cmd/MAX+plus II здесь
не запускались; Node нужен только для локальных тестов, не для Windows-сборки.

`uv run --with z80 python diagnostics/simulate_game_diag.py` исполняет собранный
EXE с моделями BIOS/DSS/VRAM: 18 сценариев прошли. Проверяются страницы и
FF terminator, полный ACX и его хвост, короткое чтение через проверку позиции
файла (DSS.Move_FP), произвольный DE после Read, ошибки BIOS/DSS, реальные
записи карт/графики/палитры, клавиши, оборачивание scroll и переключение страницы.
Это тест CPU-программы; FPGA и монитор он не моделирует.

Проверка внешнего загрузчика (нужны C-компилятор, sjasmplus, uv/z80 и указанные
внешние исходники/готовые runtime+symbols+PAK):

```sh
uv run --with z80 python tools/test_titd_acx.py \
  --titd-src /path/to/titd/src --bios-root /path/to/sprinter_bios
```

13 сценариев прошли: TITDREV выбирает K50, передаёт неизменённый ACX в цепочке
1…4 страниц, принимает ровно 65536 и отвергает 65537; реальные BIOS header check
и bit sender исполняются в Z80, подтверждены zero-run 1/254/255/256/1024 и LSB-first.
Параметр `--acx /path/to/K50.ACX` добавляет проверку настоящего Windows-результата.
Локально такой результат ещё не получен: использовались синтетические потоки
из штатного C packer. Эти проверки не доказывают fitting и запуск FPGA.

Для K50 обязательные изменения загрузчика TITDREV не установлены. Проверенный
штатный runtime передаёт сжатый K50-поток без изменений; его 13 сценариев прошли
также при намеренно произвольном `DE=DEADh` после каждого DSS.Read. Размер
запроса сохраняется на стеке: возвращаемое DE результатом API не считается.
Ранее предложенная проверка DE удалена, соответствующее замечание к TITD снято.

Внешний TITDREV содержит отдельную общую ошибку заполнения хвоста: `ADD HL,BC`
не меняет Z, поэтому `JP NZ` проверяет старый флаг. Это не различие K30/K50 и
не доказательство нарушения стабильной загрузки; сам payload читается точно.
[tools/titdrev_acx.patch](../tools/titdrev_acx.patch) теперь содержит **только**
`LD A,H / OR L`, явно устанавливающие Z по результату вычисления. Патч необязателен
для первого испытания K50; сначала используйте существующий рабочий TITDREV.
`--loader-patch` собирает временную копию и проверяет FF tail: 13 сценариев прошли.
Внешнее дерево TITD не изменено. При необходимости переноса примените патч из
`titd/src` (`patch -p1 -i /path/to/tools/titdrev_acx.patch`) и пересоберите TITDREV
штатным Makefile. Код тестов BIOS/DSS — модели API, не исполнение всей DSS.

`make -C diagnostics` собирает `diagnostics/build/GAMEDIAG.EXE` (sjasmplus,
Python 3). Подробности — [diagnostics/README.md](../diagnostics/README.md).

## TITD и приёмка платы

Нужен существующий **TITDREV** с BIOS-assisted external ACX loader. Положите
проверенный **game** `K50.ACX` рядом с игрой и её PAK. BIOS должен возвращать
имя K50 через `Fn_Cript.AcexAndBitstream` (BC=02EDh), поддерживать custom
`AcexSetUpNow` (A=FEh, C=F3h), soft restart и восстановление ROM-конфигурации.
DSS — не ниже 1.70 build 998, как проверяет Reverse loader. Единой достаточной
цифры версии BIOS по просмотренным исходникам не установлено: проверьте эти
функции в своей сборке. Оригинальный TITD/TITD0 использует ресурс `GAME_00.ACX` с 256-байтным
загрузочным кодом и встроенным K30; новый внешний `K50.ACX` с ним несовместим.
Переименование `K50.ACX` в `GAME_00.ACX` не исправляет несовместимость.
Если TITDREV переименован в `TITD.EXE`, формат определяется его кодом, не именем.

До теста сохраните рабочую стандартную K50-конфигурацию и способ её загрузки
через штатный ROM/JTAG. Проверяйте сначала временную SRAM-конфигурацию, без замены
ROM-битстрима. При невозможности штатного выхода выключение/включение возвращает
стандартную конфигурацию ROM; затем при необходимости восстановите рабочий SOF
через JTAG. Диагностика по Q выполняет hard reset. В TITDREV отдельно проверьте
обычный выход в DSS и повторный запуск без перезагрузки.

Пришлите каталог сборки (минимум report, log, floorplan audit, hashes) и результаты:

- стандартный K50 работает; новый game успешно fit в один EP1K50QC208-3;
- reviewed register-to-register и I/O пути для CLK42 с периодом 23,81 нс;
  все derived clocks, CT5/INTT, асинхронные COPY_SINC и SRAM/DAC paths отдельно;
  сохранённое штатное требование 100 МГц не заменяет эту проверку;
- нет непроверенных warning об ignored assignments, потерянных регистрах,
  неопределённых сигналах, нескольких драйверах, truncated arithmetic;
- диагностика: первый/последний пиксель, первая строка, X/Y 0…15,
  скролл через границы, страницы 0/1, стабильный монитор;
- TITD: загрузка, меню, игра, движение, сцены, неподвижный UI, клавиатура,
  звук, выход и повторный запуск.

MAME использовался как источник информации (`screen_update_game`, `as_mode`),
а TITD — как источник формата (`video_page_helpers`, low-RAM descriptor writers,
`patches/reverse_branch.asm`, `reverse_defs.inc`). Путь локальных внешних деревьев:
`../..` относительно проекта не фиксирован; в эту поставку их код не включён.
MAME не исполняет синтезированную FPGA; узнавание нового ACX по хэшу не является
проверкой. Без оригинальной game FPGA на K30 недокументированные эффекты остаются
гипотезами. Завершение приёмки требует модели, Windows-сборки **и** реального K50.
