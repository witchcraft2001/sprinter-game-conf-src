# GAME_K50: опытная конфигурация EP1K50QC208-3

Предыдущая версия собрана пользователем и запускает игру на K50: скролл работает,
но на VRAM **IS61C1024-15N** видны мигающие полоски/пиксели, в том числе на статике.
Происхождение стандартной 1K50-конфигурации в BIOS неизвестно.
После применения патча HOLD в TITD пользователь подтвердил оставшееся смещение
влево, предположительно на 16 экранных точек. Более ранние наблюдения положения
были сделаны до исправления чтения CMOS и не служат основанием для привязки X.
Добавлена поправка выборки X на −8 байтовых пикселей: изображение сдвигается
вправо на одно знакоместо. Y и физические счётчики не изменены.
Поправка общая для game K30/K50. Пересборка 14 октября успешна:
TG42 fmax K30 **44,84 МГц**, K50 **45,04 МГц**; проверка платы ещё нужна.
13 октября пересмотрены переполнения: X bitmap больше не переносится в Y;
scroll больше не обрезается по размерам физического растра. Результаты
оптимизации ниже относятся к сборкам **до** этих изменений и поправки X.
MAX+plus II запущен в текущем Windows-окружении; новые отчёты и ACX получены.
Аппаратная работа после последних изменений ещё не подтверждена.
Удалённые изменения обрезки правого border и проверок build-пакера сохранены;
для итоговой версии после изменения переполнений fitting reports получены;
проверка скролла TITD на плате ещё нужна.
Локально проверяются спецификационная модель, выражения read pipeline из TDF,
упаковка, код загрузчика TITDREV/BIOS в Z80 и диагностическая DSS-программа.
Для более ранних вариантов fitting reports получены; они не подтверждают
сборку после изменений переполнения и обрезки border. Измеренные задержки
SRAM/RGB на плате ещё не получены.
Ограниченный интерпретатор исполняет
выражения и CLK42-регистры read pipeline, но не весь AHDL и не netlist.
Результаты кодревью и незавершённые пункты — в [REVIEW_GAME_K50.md](REVIEW_GAME_K50.md).

Для той же игровой конфигурации под `EP1K30QC208-3` запустите
`altera\acex\make_game_k30.bat`. Используются общие исходники `K50` и
`GAME_K50/VIDEO2.TDF`, а целевое устройство во всех staging-ACF меняется на K30.
Обе цели используют восемь регистров prefetch скролла. Для K30 `k50_build.js`
в staging убирает промежуточный регистр суммы X: её входы стабильны в CT=0..1,
итоговый регистр X и выдача SRAM в CT=2 сохранены.
При обратном входе после border K30 удерживает только MODE0,
а K50 — MODE0…3. K30 фиксирует физическую границу в CT=2; K50 в CT=5
объединяет её с признаком graphics и удерживает вместе с MODE0.
Для каждой цели этот вариант выбран по результату fitting.
Подстановки проверяют точное совпадение исходных блоков и при их изменении
требуют пересмотра трансформации. Фазы шины и отображаемый RGB у вариантов одинаковы;
адрес неиспользуемого чтения графики во время удержания border может различаться.
Каждый запуск создаёт отдельный каталог `altera\acex\build\GAME_K30-число-число`.
После успешной компиляции и проверки он содержит готовый **несжатый** `K30.ACX`,
побайтово равный `STREAM30.BIN`, отчёт и логи. Для K30 упаковщик не запускается;
`K30.packed` и `roundtrip.bin` не создаются. K50 по-прежнему использует zero-RLE.
Проверка требует ровно один `Device: EP1K30QC208-3` в отчёте и заголовок
`FF FF 62 7B 39 00` в потоке, совпадение с TTF, непустой SOF и размер ACX
не более 65536 байт. После копирования проверяется побайтовое равенство ACX и потока.
Полный путь к готовому ACX выводится строкой `Packaging passed`.

Нужны MAX+plus II (по умолчанию `C:\MAXPLUS2\MAXPLUS2\MAXPLUS2.EXE`), штатные Windows
`cmd.exe`, Windows Script Host (`cscript.exe`) и `ADODB.Stream`. Python, grep, Unix shell и Quartus для FPGA-сборки не нужны.
Если MAX+plus II установлен иначе, задайте `MAXPLUS2_EXE` полным путём к EXE.
Без этой переменной проверяются сначала указанный путь, затем исходный
`C:\MAXPLUS2\MAXPLUS2.EXE`. Явный неверный путь считается ошибкой.

1. Запустите `altera\acex\make_standard_k50.bat`. Сначала проверьте этот SOF на
   плате: стандартный экран, память, клавиатуру, звук и акселератор.
2. Затем запустите `altera\acex\make_game_k50.bat`.
3. Каждый запуск создаёт новый `altera\acex\build\VARIANT-число-число`.
   Совпадение имени каталога считается ошибкой; существующие файлы не используются.
   `make_k50.bat` вызывает чистую **стандартную** сборку и после проверки
   публикует её проверенный **сжатый** поток в `altera/acex/STREAM.BIN` для старой
   сборки BIOS (копия standard `K50.ACX`). `STREAM50.BIN` остаётся несжатым
   промежуточным файлом. Исходный K30 `make.cmd` выдаёт **несжатый** `STREAM.BIN`.
   `make_standard_k50.bat` и `make_game_k50.bat` оставляют результаты в рабочем
   каталоге; game не может публиковаться как BIOS `STREAM.BIN`.
4. В каталоге сохраняются исходники, `source-files.txt`, `variant.txt`,
   `floorplan-audit.txt`, все диагностические файлы компилятора,
   `compile.log`, `SP2_ACEX.rpt`, `SP2_ACEX.sof`, `SP2_ACEX.ttf`,
   `STREAM50.BIN`, `K50.packed`, `roundtrip.bin` и после успешной проверки `K50.ACX`.
   Ошибка обязательного этапа возвращает ненулевой exit code. Логи не удаляются.
   `acx-sha256.txt` содержит результат дополнительного вызова штатного certutil;
   его отсутствие не заменяет и не отменяет проверки содержимого.

Сборка подставляет только `GAME_K50/VIDEO2.TDF` поверх общих файлов `K50`.
Интерфейс `video2`, экземпляр `video2:SVIDEO`, назначения физических выводов,
логика CPU, акселератора, звука и периферии сохраняются. В staging-копиях всех
ACF выбран `EP1K50QC208-3` для конкретного устройства и timing synthesis.
AUTO_DEVICE-списки не управляют явно выбранным top-level устройством.

Наследованные размещения LC/EAB сохраняются **в обеих сборках** и перечисляются
в `floorplan-audit.txt`. Слепое удаление изменяло бы базовую конфигурацию и
физические задержки LCELL write-тракта. Валидность размещений для K50 и
предупреждения ignored assignments нужно проверить по fitting report. Наличие
аудита не означает успешного размещения. Оригинальные K50 ACF не меняются.

Упаковка использует существующие `transttf.exe` и `Altera0pak.exe`. Проверка:
успех в отчёте, ровно один целевой Device K50, непустые новые SOF/TTF,
строгое соответствие каждого байта TTF/STREAM50, K50 header `FF FF 62 7B 3C 00`,
распаковка штатным packer и независимая проверка zero-run формата. Размер
сжатого ACX должен быть **1…65536 байт**. Превышение запрещает выпуск, без усечения.
В распакованном потоке K50 имеет байт `3C`, K30 — `39`. Сжатый файл начинается
`FF FF 62 7B 3C 00 nn`: `nn` — ненулевой счётчик первого zero-run
(обычно 01; нули после заголовка могут увеличить его). BIOS распознаёт
сжатый K50 по несовпадению с несжатым ROM-заголовком K30 в
`loader/bitstream_header.inc`. В ACX нет EXE-header, длины или 256-байтного
загрузочного префикса: первый байт файла — первый байт zero-packer потока. `package-verification.txt` подтверждает только упаковку.
Для GAME_K30/GAME_K50 перед выпуском ACX дополнительно проверяется строка
`fmax … TG42 to register …` из таблицы timing report. Берётся **Actual Value**,
а не требование 100 МГц: достигнутый минимум должен быть **строго >42 МГц**.
Отсутствующая/непонятная строка или значение <=42 завершают сборку с ошибкой,
сохраняя SOF/TTF/raw/packed/report/log для разбора, но без готового ACX.
Порог не применяется к контрольной STANDARD_K50. Он не заменяет проверку
производных тактов, внешних SRAM/RGB setup/hold и платы.
Не копируйте ACX из каталога предыдущего запуска при ошибке нового.

## Дескриптор и адресное пространство

VRAM — 256 КиБ, 256 строк по 1024 байта, четыре SRAM банка по 64 КиБ.
Логический байт `a` хранится в `VDM[3-(a & 3)][a >> 2]` (видно также из `V_EN3…0`
общего write-тракта). Физические адресные выводы `VAO = VLA[17:2]`.

| Байт | Банк | Семантика game |
|---|---|---|
| MODE0 | VDM3 | биты 1:0 — X[9:8]; бит 2 — загрузить скролл; биты 7:6 — палитра |
| MODE1 | VDM2 | X[7:0], допускается любой адрес, включая невыровненный |
| MODE2 | VDM1 | Y[7:0] |
| MODE3 | VDM0 | младший полубайт — X scroll 0…15; старший — Y scroll 0…15 |

В TITD `src/runtime/entry_runtime.asm` находятся исходные четвёрки
`F4 00 00 00`, `F4 00 00 80`, серия `24 00 00 0F`, затем `E4 00 00 00`.
Они подтверждают отдельный четвёртый байт и загрузку горизонтального/вертикального
смещения, а не часть пиксельных данных. Разложение X/Y проверяется по game renderer
и организации штатного VRAM; точный момент применения в оригинальном FPGA неизвестен.

MODE0[5:3] участвуют в специальных режимах; в обычной game-графике нет
разделения байта на два цвета. Один байт задаёт индекс 0…255. Визуальное
удвоение по горизонтали в MAME не превращает этот формат в 4bpp.
Отдельные режимы 640 пикселей и текста по MODE0[4]/[5] не реализованы:
вне border/blank используется байтовая графика 320 пикселей. Это ограничение
game-варианта, не полная реализация всех битов из комментария RELOAD.

Адрес дескриптора: `(page<<17) | (column<<11) | 0x700 | (row<<2)`.
Здесь `column=sample_x/8`, `row=sample_y/8`, page=`DIR_PORT3`.
Это нечётная строка каждой пары, соответствующая четырёхбайтовым записям TITD
и штатной форме `(DIR_PORT3, CTH, CT5, 11b, CTV[8:3], 00b)` при CT5=1.
Физический растр содержит 56 столбцов и 40 строк, включая невидимые.
Поля номера столбца и строки в адресе имеют по 6 бит; скролл может выбрать
дескрипторы за физической областью — до столбца 57 и строки 41 при offset 0…15.
Это не означает, что вся область 64×64 свободна: верхние строки адресного поля
пересекаются с палитрой. Формат ресурсов и размещение таблицы не менялись.

```
raster_x = (physical_x - 8) mod 448
sample_x = (raster_x + scroll_x) & 511
sample_y = (physical_y + scroll_y) & 511
```

Здесь modulo 448 относится только к фиксированной привязке физического
растра: первая физическая клетка следует за клеткой 55. Он выполняется **до**
прибавления scroll. При нулевом scroll сохраняется поправка вправо на знакоместо
(8 байтовых пикселей / 16 точек). Скролл не оборачивается на 447/319:
`raster_x=447, scroll_x=1` выбирает X=448 (столбец 56), а
`physical_y=319, scroll_y=1` выбирает Y=320 (строка 40).

Физические CT/CTH/CTV и COPY_SINC не зависят от scroll. CTV увеличивается
в конце CTH=48, X оборачивается после CTH=55. При действительном переходе
CTV 319→0 следующий запрос использует Y=0+scroll, а не 320+scroll.
Комментарий RELOAD о переходе 55-го/56-го знакоместа объясняет обход физического
растра и наследование scroll, но не доказывает modulo 448 у суммы со scroll.

CT=0 складывает координаты и фиксирует признаки физических границ.
CT=1 корректирует начало X шестибитным сложением/вычитанием номера клетки;
граница выбирается по физической позиции, не по сумме со scroll. Переход кадра
исправляется выбором младших четырёх битов суммы Y. CT=2 выдаёт дескриптор.
Дополнительного широкого сумматора между регистрами не добавлено. Физические
задержки после нового fitting всё равно требуют проверки.

При проверке вертикального смещения обнаружено отдельное несоответствие во
внешнем `titd/src/runtime/patches/reverse_branch.asm`: после загрузки конфигурации
CMOS читается с `D=0`, результат пишется в HOLD. В доступном дереве BIOS
`Shared_Includes/constants/SP2000.inc` задаёт `CMOS_CELL.ScreenPosition=1Fh`,
а `CMOS.Register.seconds=00h`; `src/bios/exp/FUNC_CMOS.ASM` передаёт D напрямую
в адрес CMOS. Setup `XY_SCREEN` использует именно ScreenPosition.
Поэтому для этой версии BIOS такой код TITDREV записывает в HOLD секунды вместо
положения экрана. GAMEDIAG исправлен на `D=1Fh`; внешнее дерево TITD не изменено.
Подготовлен отдельный [titdrev_hold.patch](../tools/titdrev_hold.patch), меняющий
только адрес CMOS в TITDREV. Пользователь сообщил о применении и запуске патча;
после этого обнаружено описанное выше остаточное смещение влево. Для BIOS с указанной картой
CMOS его можно применить из `titd/src` командой
`patch -p1 -i /path/to/tools/titdrev_hold.patch` и пересобрать игру.
Это возможная причина разницы положения, но не доказанная причина ровно 8 строк
на плате: нужно сопоставить фактические BIOS/EXE и HOLD при сравнении конфигураций.
Формат ACX и передача битстрима от этой настройки не зависят.

В этой реализации адрес графики определён так:

```
xbase = ((MODE0 & 3) << 8) | MODE1
ybase = (MODE2 + (sample_y & 7)) & 255
x = (xbase + (sample_x & 7)) & 1023
address = (ybase << 10) | x
```

X и Y переполняются независимо: (X=1023, Y=10) + local_x=1 даёт (0,10),
а не (0,11); Y=255 + local_y=1 даёт Y=0. После регистров CT=6 адрес получается
конкатенацией полей: перенос из X в Y и его сумматор перед VLA удалены.

Основание — раздельные 10-битное X и 8-битное Y в дескрипторе и виртуальный
экран 1024×256 из `games/game_conf/tests/RELOAD.ASZ:366–395`, плюс замечание
ревьюера. Комментарий не описывает все переполнения явно: это выбранная
семантика новой FPGA, не доказанное совпадение с исходным K30 game-битстримом.
Доступный MAME использует линейный перенос X и modulo размеров растра для scroll;
на этих границах он теперь отличается от проекта. Он не исполняет FPGA и здесь
не используется как эталон. Тесты проверяют отдельные поля, различимые данные
по обе стороны границ, обе страницы и все значения scroll.

Скролл — последовательное состояние с нулевым power-up. Управляющий
дескриптор принимается при изменении его адреса (включая номер страницы),
а не при каждом повторном чтении того же адреса. Повторный вход в клетку
считается новым принятием. При первом захвате control его MODE3 сохраняется
в G_PENDING. Для графического control используется ближайшая граница: конец
исходной клетки (G_LOCAL_X=7) **или физического экранного знакоместа**.
Border/blank control по-прежнему завершается при G_LOCAL_X=7.
На CT=2 pending однократно загружается в scroll и через G_EFFECTIVE участвует
в адресе следующего запроса. Физическая граница помечается отдельным регистром
заранее для prefetch. Прежняя трактовка комментария RELOAD «на следующем
знакоместе» как обязательного конца всей сдвинутой исходной клетки была неверна
для правого столбца TITD. Запись CPU в MODE3 уже занятой клетки применяется
при следующем входе. При принудительной смене страницы/строки внутри клетки
pending сохраняется до следующей подходящей границы; новый control заменяет ещё не применённый
pending. Последний пограничный случай — явно выбранная семантика, не доказанная
эквивалентность оригинальному K30. Сброса на строке/кадре и MAME lookback нет.

Исключение для обратного входа после border/blank: если X scroll уменьшается
более чем на 8, `G_BACKTRACK` удерживает MODE0 до конца повторно выбранной
предыдущей клетки. Её control также не принимается. MODE1…3 и SRAM-слоты
продолжают обновляться; пиксельные данные во время border не выводятся.
На следующем local X=7 удержание снимается перед захватом нового дескриптора.
Это занимает 1…7 байтовых пикселей, не переносится на следующую клетку и не
меняет применение scroll у графических управляющих дескрипторов.

Прежний дефект модели найден по локальным исходникам `C:\Users\Dmitry\dev\sprinter\titd`:
`src/runtime/entry_runtime.asm` задаёт графический seed `24,0,0,0F` и border `E4,0,0,0`;
`src/pak/code/raw_gap0_lowram.asm`, процедура `lowram_object_step_d`, помещает
border seed в столбец 40. Графический seed находится в столбце **39**, не слева:
после `ADD A,27h` и `EX DE,HL` адрес назначения уже сдвинут на 39 столбцов.
Этот момент был неверно разобран в первой попытке исправления правого края.
В изолированном тесте с X scroll=15 бордюр начинается в physical X=313.
После его восьмого пикселя сброс в 0 раньше возвращал выборку в X=313, столбец 39:
графика повторно появлялась на physical X=321…327. Теперь эти семь пикселей
сохраняют border; служебная команда из повторно выбранной клетки не исполняется.
Размер поля и номер столбца в FPGA не зашиты. Тест перебирает все 16×16 пары
старого/нового X scroll на обеих страницах, проверяет видимый пиксель перед
бордюром и отсутствие возврата графики за ним. Отдельно проверяются E4/F4/FC/FD/FE/FF,
смена Y, сохранение blank/IRQ и снятие удержания перед следующей графической клеткой.

G_VALID удалён: G_LAST=0 при старте отличается от любого адреса дескриптора,
в котором всегда есть биты 111. Нулевые power-up G_SCROLL/G_PENDING_VALID/G_LAST
нужно подтвердить в netlist MAX+plus II для ACEX. Интерпретатор и модель задают
нулевое начальное состояние; это само по себе не проверка аппаратной инициализации.

| MODE0 | Отображение | Scroll | Interrupt request |
|---|---|---|---|
| 24h | байтовая графика, палитра 0 | да | нет |
| E4h, F4h | border, индекс 400h + 9×BRD | да | нет |
| FCh, FEh | blank, индекс 400h | да | нет |
| FDh, FFh | blank, индекс 400h | да | да |

Общий признак border — MODE0[7:5]=111; blank дополнительно требует bits3:2=11
или DIR_PORT4. Interrupt дополнительно требует bit0=1; как в исходнике,
активный низкий INTT регистрируется по фронту **бита CT[5]** при физических
CTV[2:0]=7. Это производный такт внутри клетки, а не фаза CT[2:0]=5.
Обычные палитры выбираются индексом `(MODE0[7:6]<<8)|color`.
Для палитры 3 обычные дескрипторы используют C0h…DFh, не E0h…FFh.

## Фазы чтения

Таблица показывает **значения до фронта CLK42**. Один период — 23,81 нс.
Для пикселя и дескриптора адрес держится **два периода**, то есть 47,62 нс
от фронта выдачи до фронта захвата. Из этого бюджета вычитаются clock-to-output
FPGA, задержки платы, SRAM, входная трассировка FPGA, mux банка и setup.
Hold на фронте смены адреса проверяется отдельно. Палитра для внешних RGB-регистров
по-прежнему имеет один период: у неё отдельный путь без обратного входа в FPGA.

| CT[2:0] | VCM | После фронта VLA | Захват до смены адреса |
|---|---|---|---|
| 0 | 5 | пиксель | внешние RGB-регистры захватывают предыдущую палитру |
| 1 | 1 | тот же пиксель | — |
| 2 | 4 | дескриптор следующего физического пикселя | цвет текущего пикселя, метаданные; при local X=7 применить pending; координаты/адрес следующего запроса |
| 4 | 3 | тот же дескриптор, адрес из G_REQUEST | — |
| 5 | 2 | исходное окно CPU/акселератора | MODE0…3, сохранение нового control в pending |
| 6 | 0 | палитра | штатное продвижение растра |

Неиспользуемые внутренние WR_MODE/WR_PIC/WR_COL и X_MODE_BOND удалены.
Game-регистры захватываются общим CLK42 с enable VCM=2 (CT=5).
Захват не зависит от задержки производного LWR_MODE. G_REQUEST удерживает адрес
второго descriptor slot даже при смене DIR_PORT3 между CT=2 и CT=4.

Раньше одинаковая палитра читалась дважды за байтовый пиксель. Теперь ранний
palette slot CT=2 занят дескриптором. **WR_PIX/WR_COL на плате имеет только один
положительный фронт — CT=0 после palette slot CT=6**; иначе RGB-регистры захватили
бы дескриптор и показали полосы. Длительность одного отображаемого байтового
пикселя остаётся шесть CLK42. Начало его отображения сдвинуто на три CLK42
(71,43 нс, половину байтового пикселя) относительно прежнего раннего строба CT=4.
Границы изображения нужно проверить диагностикой; физические счётчики и sync
не менялись. В исходниках MAX `XACS=WR_COL` используется для определения наличия
конфигурации (`CNF_OFF`), а не как делитель видеочастоты; импульсы сохраняются.
Общее окно CPU/акселератора и LCELL write-тракт сохранены. Однако новый fitting
может изменить физические задержки даже при неизменных уравнениях записи.

## Артефакты и материалы SP_Conf_Test

Цель, уточнённая пользователем: **один и тот же K50.ACX** для Winbond
W24512/W241024, Alliance AS7C1024 и ISSI IS61C1024 класса **15 нс**, с одинаковыми
растром, скоростью и поведением игры. Поддержка 20/25 нс в эту цель не входит.
Двухтактное чтение не зависит от производителя: в TDF нет выбора марки SRAM
или отдельного расписания для ISSI. Однако совместимость всей прошивки с этими
семействами ещё не подтверждена.

Для общего варианта принимаются худшие ограничения **по каждому параметру**,
а не один условный «самый медленный чип». Проверка должна включать:

- Чтение в FPGA: при tAA=15 нс остаётся 32,62 нс на clock-to-output, плату,
  обратный входной путь/mux, setup и неблагоприятный skew.
- Чтение палитры во внешние RGB-регистры: при tAA=15 нс остаётся только
  8,81 нс на остальные задержки/setup/skew. Удвоение окна чтения FPGA не
  увеличивает это окно; его проверяют отдельно.
- Hold: минимальные задержки смены VA и данных относительно фронта захвата.
  Проверка только максимального tAA и Fmax недостаточна.
- Запись: минимальная длительность физического /WE, время валидности адреса
  и VD до конца записи, удержание VD после неё, отпускание и повторное включение
  выходов SRAM. Учитывается подключение /OE к земле, а не условия OE=1 из
  отдельной паспортной таблицы. Номинальные полтакта CLK42 и число LCELL не
  являются измерением импульса на выводе.

Например, у IS61C1024 параметр длительности /WE в таблице помечен как проверенный
при OE=1; для OE=0 приведена отдельная диаграмма переключения шины.
[ISSI, страницы 7–9](https://media.digikey.com/pdf/Data%20Sheets/ISSI%20PDFs/IS61C1024%2CL.pdf).
Alliance AS7C1024 из архива и AS7C1024B имеют разные параметры записи:
нельзя переносить цифры между ревизиями только по общему имени семейства.
[AS7C1024B, страницы 6–7](https://www.alliancememory.com/wp-content/uploads/AS7C1024B-12TJIN_AS7C1024B_March2022_v3.0.pdf).
В локальной модели сейчас проверяется чтение с отдельными задержками FPGA/DAC;
она не подтверждает общую совместимость по записи и hold.

Аппаратная приёмка общего варианта требует испытать **одинаковый ACX с тем же
SHA256** на перечисленных SRAM: статический GAMEDIAG, скролл/страницы и интенсивная
запись CPU/акселератором. Для каждой платы фиксируются полная маркировка памяти,
результат и соответствующий fitting/timing report. Подбор отдельной LCELL-цепочки
для каждой марки не считается достижением цели одной общей прошивки.

В предоставленном `SP_Conf_Test.7z` изучены `altera/acex/VIDEO2.TDF`,
`INFO_MD/Video-Mem.md`, `Test3.md`…`Test7.md`, `AHDL_PLAYBOOK.md` и описание
подключения памяти/RGB-регистров. В TDF есть профили `ORIG_WINBOND`, `RR2`,
`TEST_A`, `TEST_B`: они меняют прежде всего LCELL-цепочки `/WE` и разрешения
драйверов VD. Текущий общий тракт похож на RR2, но отличается F_WR.
Заметки описывают эксперименты с разными SRAM и содержат предложения, которые
не все перенесены в итоговый TDF. Подтверждённого универсального профиля для
нашей game-сборки и IS61C1024-15N в изученных материалах не установлено.

Поэтому первая правка устраняет конкретный недостаток собственного game read
pipeline: цвет захватывался через один такт, хотя адрес держался два; дескриптор
читался за один такт. Для класса -15 паспортное tAA равно 15 нс — только задержка
микросхемы, а не всего пути. [Даташит ISSI, Read Cycle Switching Characteristics](https://media.digikey.com/pdf/Data%20Sheets/ISSI%20PDFs/IS61C1024%2CL.pdf).
Остававшиеся 8,81 нс могли быть недостаточны для FPGA и платы. Это обоснованная
гипотеза причины мерцания, а не измеренное нарушение на конкретной плате.
Изменения загрузчика TITD и формата ACX для этой правки не нужны.

После пересборки `make_game_k50.bat` сначала запустите GAMEDIAG и оставьте экран
без нажатий: после инициализации и отпускания клавиш программа не пишет VRAM.
Сравните мерцание, швы клеток и левую/правую границы с предыдущей game-сборкой,
затем проверьте все смещения и TITD. Если мерцание осталось, нужны report/log
новой сборки и результат свежей стандартной сборки на тех же микросхемах.
Стандартная конфигурация из неизвестного BIOS не заменяет такое сравнение.

Оставшиеся физические проверки: VA→SRAM→MODE/G_COLOR за два периода; VA→SRAM→RGB
и WR_COL setup/hold за один период; восстановление шины после CPU write;
ширина `/WE`, удержание VD до конца записи и отсутствие конфликта драйверов.
Для них нужны post-fit пути и, при необходимости, измерения на плате. Модель
не симулирует LCELL-задержки, ёмкость линии WR_COL, аналоговые уровни и bus contention.

дескриптора на CT=2. В приведённых ниже сборках вычитание 448/320 выполнялось

Затем 13 октября оборачивание scroll по 448/320 удалено, оставлены только
поправки физических границ. Перенос X в Y для bitmap также удалён.
В опубликованных ниже результатах ещё использовались прежние суммы с переносом X в строку. Маски пяти адресных слотов
декодируются заранее. Цвет border фиксируется вместе с пикселем на CT=2, чтобы
запись CPU между CT=2 и CT=6 не изменяла уже выбранную палитру. Условие захвата
записи выражено в активной полярности без принудительной LCELL и инвертора;
его таблица истинности сохранена. Растр и цепочки задержек `/WE`/VD сохранены.
Клавиатура, IRQ/hotkeys и мышь в этих результатах не отключены.

Оба используют 14080 бит памяти и 5 EAB. `Packaging passed` подтверждает
компиляцию/упаковку и побайтовый roundtrip, но не тайминг всей платы.

В этих прежних сборках критический TG42 путь K50 проходит от RAM декодера `DECODE.MEM` к
инвертированному регистру `:1488` (формирование `SVIDEO.wr` в `SP2_ACEX.TDF`).
На K30 это `/IOWR` → `SVIDEO.VXA0`. Исходное требование 100 МГц в ACF не
изменено, поэтому соответствующая строка отчёта всё ещё имеет `Failed`.
MAX+plus II предупреждает о preliminary timing, ripple clocks и нерассчитанных
путях между разными clocks. Значение TG42 не закрывает внешние setup/hold,
производные clocks и асинхронные входы.

Пользователь подтвердил RGB-регистр **74HC374, 5 В**, TG42 **42 МГц**.
Для SRAM IS61C1024-15N максимальный tAA равен 15 нс. В даташите Nexperia
74HC374 при VCC=4,5 В setup составляет минимум 12 нс при 25 °C и 15 нс
в диапазоне −40…+85 °C; hold — 5 нс. При нулевом относительном сдвиге
VA/WR_COL уже 15+12=27 нс превышают однотактный бюджет палитры 23,81 нс.
Это расчёт по гарантированным параметрам, а не измерение фактической задержки.
Точный производитель HC374, задержка WR_COL относительно VA и оба края hold
должны учитываться отдельно. Паспортный запас на 42 МГц пока не подтверждён.
[Nexperia HC/HCT374, таблица 7](https://assets.nexperia.com/documents/data-sheet/74HC_HCT374.pdf),
[ISSI IS61C1024, Read Cycle](https://media.digikey.com/pdf/Data%20Sheets/ISSI%20PDFs/IS61C1024%2CL.pdf).

Для гарантии работы без артефактов нужно закрыть этот внешний путь: регистр
с меньшим гарантированным setup либо перераспределение фаз чтения палитры с
повторной проверкой CPU/write и растра. Произвольная задержка RGB-строба может
нарушить hold при переключении SRAM на пиксель; рост внутреннего fmax её
не заменяет. Проверка платы GAMEDIAG/TITD остаётся необходимой.

## TITD и приёмка платы

Нужен существующий **TITDREV** с BIOS-assisted external ACX loader. Положите
проверенный **game** `K50.ACX` рядом с игрой и её PAK. BIOS должен возвращать
имя K50 через `Fn_Cript.AcexAndBitstream` (BC=02EDh), поддерживать custom
`AcexSetUpNow` (A=FEh, C=F3h), soft restart и восстановление ROM-конфигурации.
DSS — не ниже 1.70 build 998, как проверяет Reverse loader. Единой достаточной
цифры версии BIOS по просмотренным исходникам не установлено: проверьте эти
функции в своей сборке. Оригинальный TITD/TITD0 использует ресурс `GAME_00.ACX` с 256-байтным
загрузочным кодом и встроенным K30; новый внешний `K50.ACX` с ним несовместим.
Переименование `K50.ACX` в `GAME_00.ACX` не исправляет несовместимость.
Если TITDREV переименован в `TITD.EXE`, формат определяется его кодом, не именем.

До теста сохраните рабочую стандартную K50-конфигурацию и способ её загрузки
через штатный ROM/JTAG. Проверяйте сначала временную SRAM-конфигурацию, без замены
ROM-битстрима. При невозможности штатного выхода выключение/включение возвращает
стандартную конфигурацию ROM; затем при необходимости восстановите рабочий SOF
через JTAG. Диагностика по Q выполняет hard reset. В TITDREV отдельно проверьте
обычный выход в DSS и повторный запуск без перезагрузки.

Пришлите каталог сборки (минимум report, log, floorplan audit, hashes) и результаты:

- стандартный K50 работает; новый game успешно fit в один EP1K50QC208-3;
- reviewed register-to-register и I/O пути для CLK42 с периодом 23,81 нс;
  все derived clocks, CT5/INTT, асинхронные COPY_SINC и SRAM/DAC paths отдельно;
  сохранённое штатное требование 100 МГц не заменяет эту проверку;
- нет непроверенных warning об ignored assignments, потерянных регистрах,
  неопределённых сигналах, нескольких драйверах, truncated arithmetic;
- диагностика: первый/последний пиксель, первая строка, X/Y 0…15,
  скролл через границы, страницы 0/1, стабильный монитор;
- TITD: загрузка, меню, игра, движение, сцены, неподвижный UI, клавиатура,
  звук, выход и повторный запуск.

MAME использовался как источник информации (`screen_update_game`, `as_mode`),
а TITD — как источник формата (`video_page_helpers`, low-RAM descriptor writers,
`patches/reverse_branch.asm`, `reverse_defs.inc`). Путь локальных внешних деревьев:
`../..` относительно проекта не фиксирован; в эту поставку их код не включён.
MAME не исполняет синтезированную FPGA; узнавание нового ACX по хэшу не является
проверкой. Без оригинальной game FPGA на K30 недокументированные эффекты остаются
гипотезами. Завершение приёмки требует модели, Windows-сборки **и** реального K50.
